# seaorm-auto-audit

Automatic audit trails for [SeaORM](https://www.sea-ql.org/SeaORM/) entities.

Mark a model auditable and every create, update and delete lands in an `audits`
table with the before and after state and the user who did it — without each
route remembering to write a row.

```rust
// 1. the entity opts in
impl seaorm_auto_audit::Auditable for users::Entity {
    fn redacted_columns() -> &'static [&'static str] {
        &["password_hash"]
    }
}

// 2. the hooks are wired (in the entity module, or a hand-written module
//    next to generated entities)
seaorm_auto_audit::impl_audit_hooks!(users::Entity, users::ActiveModel);

// 3. the request carries the actor
seaorm_auto_audit::scope(Some(user_id.into()), handler(req)).await;
```

## Install

```toml
seaorm-auto-audit = "0.4"

# with the axum middleware helpers:
seaorm-auto-audit = { version = "0.4", features = ["axum"] }
```

Requires SeaORM 2.0 and Rust 1.94.0 or later.

## How it works

Three pieces, and only three:

1. **Hooks.** [`ActiveModelBehavior`](https://docs.rs/sea-orm/2.0.4/sea_orm/entity/trait.ActiveModelBehavior.html)
   lifecycle hooks on the auditable entity, delegating to one shared helper.
   The helper receives the same connection handle as the write, so the audit row
   joins the write's transaction.
2. **The actor.** A task-local holding *who* is making the change. The actor is
   optional: a request with a session carries `Some(user_id)`, a webhook or a
   background job carries `None`, and the audit row is written unattributed
   rather than skipped.
3. **The stash.** `before_save` cannot see the old row and `after_save` cannot
   see it either, so the "before" snapshot is parked on the task-local between
   the two hooks.

## Setup

### 1. The table

Use the appropriate DDL for your database backend:
- Postgres: [`sql/setup.postgres.sql`](sql/setup.postgres.sql)
- MySQL: [`sql/setup.mysql.sql`](sql/setup.mysql.sql)
- SQLite: [`sql/setup.sqlite.sql`](sql/setup.sqlite.sql)

Copy the columns into the host application's migration. The table is compatible
with any SeaORM-supported database:

| column            | meaning                                             |
|-------------------|-----------------------------------------------------|
| `id`              | primary key, generated by the crate as a UUIDv7      |
| `created_at`      | when the change happened                             |
| `auditable_table` | the table of the audited row                         |
| `auditable_id`    | the primary key of the audited row, as text          |
| `action`          | `create`, `update` or `delete`                       |
| `before_content`  | before the change (`null` for creates); the full row, except for updates, where only the changed columns |
| `after_content`   | after the change (`null` for deletes); the full row, except for updates, where only the changed columns  |
| `updated_by_id`   | the user who made the change (`null` when nobody did) |
| `ip_address`      | the client address, when there was a request         |
| `url`             | the request URL, when there was a request            |
| `user_agent`      | the request's `User-Agent`, when it had one          |

The request columns and `updated_by_id` are nullable: non-HTTP writes
(background jobs, webhooks) have neither a session nor a request behind them,
and are still audited.

One row of the trail, for an update in which the user changed their email
address and their password:

```json
{
  "id": "019a2f4c-7b1e-7f3a-9c2d-5e6f7a8b9c0d",
  "created_at": "2026-10-26T19:03:11.412Z",
  "auditable_table": "users",
  "auditable_id": "9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d",
  "action": "update",
  "before_content": {
    "email": "grace@old.example",
    "password_hash": "[redacted]"
  },
  "after_content": {
    "email": "grace@new.example",
    "password_hash": "[redacted]"
  },
  "updated_by_id": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
  "ip_address": "203.0.113.7",
  "url": "https://app.example.com/users/9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d",
  "user_agent": "Mozilla/5.0 (X11; Linux x86_64; rv:133.0) Gecko/20100101 Firefox/133.0"
}
```

The password changed, so both snapshots carry the `"[redacted]"` marker and
no hash appears anywhere in the row. Only the columns that changed appear
at all: the name and the id did not change, so they are absent, and the row
is identified by `auditable_id`. Had the password not changed, its column
would be absent too. The rules are in [Redaction](#redaction).

`auditable_id` and `updated_by_id` are stored as text rather than a fixed
column type. That lets one audit table cover tables whose keys are `uuid`,
integer or string, and lets the acting user be any of those. The crate's
[`AuditId`](https://docs.rs/seaorm-auto-audit/latest/seaorm_auto_audit/id/struct.AuditId.html)
carries the identifier and converts it to its canonical text form. Audit row
ids are generated as UUIDv7, so they sort by creation time.

The crate owns the matching entity (`seaorm_auto_audit::Audits`). If the host
application already has an `audits` table with extra columns, the extra columns
must be nullable — the crate simply leaves them out of the insert.

### 2. The entity opts in

An auditable model needs a single-column primary key and must derive
`Serialize`. The key may be a `uuid`, an integer or a string:

```rust
#[derive(Clone, Debug, PartialEq, DeriveEntityModel, Serialize, Deserialize)]
#[sea_orm(table_name = "users")]
pub struct Model {
    #[sea_orm(primary_key, auto_increment = false)]
    pub id: Uuid, // or i64, String, ...
    // ...
}

impl seaorm_auto_audit::Auditable for users::Entity {
    fn redacted_columns() -> &'static [&'static str] {
        &["password_hash"]
    }
}
```

`Auditable::audit_id` maps a row to the id stored in `audits.auditable_id`. The
default reads a single-column primary key and converts it to text through
`AuditId::from_value`, which understands `uuid`, signed and unsigned integers,
and strings. Override it for composite keys or any other key type.

### 3. The hooks

Put this in the entity module, replacing the generated
`impl ActiveModelBehavior for ActiveModel {}`:

```rust
seaorm_auto_audit::impl_audit_hooks!(users::Entity, users::ActiveModel);
```

The macro writes the four hook methods, each of which calls the shared helper
and nothing else. Writing them by hand works just as well — the logic stays in
the crate either way.

If the entities are generated (sea-orm-codegen), keep the hooks in a
hand-written module rather than in the generated file: the file is rewritten
on every regeneration. Exactly one `impl ActiveModelBehavior` may exist per
entity, and the failure mode matters — with codegen's
`--experimental-preserve-user-modifications` the generated
`impl ActiveModelBehavior for ActiveModel {}` is dropped and the hand-written
one stays; without the flag the two clash, and the build fails with a
conflicting-implementations error instead of losing the audit trail quietly.

### 4. The actor

The actor is ambient, the way Laravel's `session()` helper is: request-scoped
code reads it without arguments threaded through the call stack. SeaORM fixes
the hook signature, so there is nowhere else to put it.

```rust
// a request with a session
seaorm_auto_audit::scope(Some(user_id.into()), next.run(req)).await;

// a background job, or a webhook: nobody in particular
seaorm_auto_audit::scope(None, run_job().await).await;
```

With the `axum` feature, two middleware helpers are included:

```rust
// the app resolves the actor itself; the resolver returns Option<AuditId>
async fn audit_scope(req: Request, next: Next) -> Response {
    seaorm_auto_audit::middleware::scope_request(req, next, |req| actor_of(req)).await
}

// a resolver built on a uuid session returns Option<Uuid>, so map it
async fn audit_scope_uuid(req: Request, next: Next) -> Response {
    seaorm_auto_audit::middleware::scope_request(req, next, |req| {
        actor_of(req).map(Into::into)
    })
    .await
}

// or the app puts the actor in the request extensions
async fn audit_scope_extensions(req: Request, next: Next) -> Response {
    seaorm_auto_audit::middleware::scope_request_with_extension(req, next).await
}
```

Both capture the request details the audit row records: the client address,
the URL and the `User-Agent`.

The address is resolved by [`axum-client-ip`](https://docs.rs/axum-client-ip).
Install a `ClientIpSource` extension naming the header your trusted edge sets:

```rust
use seaorm_auto_audit::middleware::ClientIpSource;

let app = Router::new()
    .route("/users", post(create_user))
    .layer(from_fn(audit_scope))
    .layer(ClientIpSource::XRealIp.into_extension());
```

Only choose a header that the edge overwrites on every request, and install the
source outside the audit scope so the middleware sees it. Without a configured
source, an address the application already resolved into the crate's `ClientIp`
request extension is used, and then the connection's peer address
(`ConnectInfo`), which behind a proxy is the proxy's address. If a source is
configured and its header is missing or not an address, the audit row records
no address rather than falling back to the proxy's.

The URL is built from the request URI and the request's `Host` header. Its
scheme is the one the request arrived on, read from `X-Forwarded-Proto` when
that header holds `http` or `https`, with `http` as the fallback when the
request carries no scheme at all. `X-Forwarded-Host` is not used: the host
comes from the `Host` header.

`seaorm_auto_audit::current_user_id()` returns the acting user of the current scope as an
`Option<AuditId>`, or `None` outside a scope and for machine-made changes.
`seaorm_auto_audit::current_request_metadata()` returns the request details, or
`None` for machine-made changes. To scope a non-HTTP write with the same
attribution, use `scope_with_request`.

### The layer order matters

The scope has to sit *inside* the layer that resolves the actor, because the
scope captures the actor when it opens. axum runs the layer added last first,
so the auth layer goes last:

```rust
let protected = Router::new()
    .route("/users", post(create_user))
    .layer(from_fn(audit_scope))        // inner: opens the scope
    .layer(from_fn(require_session));   // outer: runs first, knows the actor
```

With the extension variant, the auth layer puts the actor in the request
extensions and the scope reads it back:

```rust
req.extensions_mut().insert(seaorm_auto_audit::middleware::Actor::new(user_id));
```

## Redaction

Two rules, and the second one is the interesting one:

1. On create and delete, redacted columns are dropped from the snapshot
   outright. The action already says the row was created or removed.
2. On update, the raw values are compared *first*, while both are still in
   memory. A redacted column that did not change is dropped from both
   snapshots; a redacted column that did change is written as `"[redacted]"` on
   both sides.

Naive redaction breaks the "it changed" requirement: both snapshots are full
rows, so replacing a password hash with a constant on both sides makes a
password-only update produce two identical snapshots. The audit row exists but
looks like a no-op, and nothing says the password was the thing that moved.
With the rules above, **a redacted column present in an audit row means it
changed, and no audit row ever holds a hash**.

The same principle applies to every column, not just redacted ones: an
update's snapshots hold only the columns that changed, so the pair is the
diff rather than two full rows. An update that changed nothing writes no
audit row at all. Creates and deletes hold the full row, because there the
whole row is the change.

A third list, `excluded_columns()`, covers columns that should not be
recorded at all: no value, no marker, as if the column did not exist. Noise
belongs there, a timestamp or counter that changes on every write, and an
update that touches only excluded columns writes no audit row. Redaction
says "this changed, but you may not see it"; exclusion says "this is not
worth recording".

## Transactions are part of the design

Hook errors behave differently before and after the write, and the difference
decides the rule.

- An error from `before_save` aborts before the write runs. Safe anywhere.
- An error from `after_save` arrives *after* the write has executed. Without a
  transaction the write is already committed, the audit row is not, and the
  handler reports failure for a change that stuck.

So: **audited writes always run inside an explicit transaction**, and the audit
insert uses the `&db` handle the hook receives, which is the transaction. The
write and the audit row then commit or roll back as one unit.

```rust
let txn = db.begin().await?;
am.update(&txn).await?;   // the write and its audit row, together
txn.commit().await?;
```

## Pruning

The crate never prunes on write and never schedules anything; removing
history is a decision the application makes on purpose, by calling `prune`
from its own maintenance job or admin tool:

```rust
use std::time::Duration;
use seaorm_auto_audit::{prune, PruneMode, PrunePolicy};

let policy = PrunePolicy {
    keep_latest: Some(100),                          // per audited row
    older_than: Some(Duration::from_secs(90 * 24 * 60 * 60)),
};
let reported = prune(&db, &policy, PruneMode::DryRun).await?;
```

The two rules combine as a union: a row is selected when it is older than
the age, or beyond the keep count for its row, or both. Both modes return
the rows in question, oldest first. `DryRun` deletes nothing, so a new
policy is inspectable before it is trusted; `Delete` removes the selected
rows inside a transaction and returns the rows it removed, so pruning and
backing up the removed history are one step. A policy with neither rule
set is refused.

## Coverage

SeaORM fires the lifecycle hooks only from `ActiveModel`'s own methods.
Repository-style writes run the SQL directly and never touch the hooks, so an
audited table written that way leaves no audit trail.

| fires hooks                        | does not fire hooks                |
|------------------------------------|------------------------------------|
| `am.insert(db)`                    | `Entity::insert(am).exec(db)`      |
| `am.update(db)`                    | `Entity::update(am).filter(..)`    |
| `am.save(db)`                      | `Entity::insert_many(..)`          |
| `am.delete(db)`                    | `Entity::update_many()`            |
| nested `builder().save()`          | `Entity::delete_many()`            |
|                                    | `Entity::delete_by_id`             |
|                                    | `update_without_returning`         |

Two extra edges: `update_without_returning` runs `before_save` but not
`after_save`, and `save()` picks insert or update purely from whether the
primary key is fully `Set`.

### The rule

> Audited tables are written only with ActiveModel methods (`am.insert`,
> `am.update`, `am.save`, `am.delete`), inside a transaction. For bulk writes,
> use the crate's audited wrappers instead of the raw methods.

Do not leave the rule as prose. The `seaorm-auto-audit-check` binary enforces it:

```console
$ cargo run -p seaorm-auto-audit --bin seaorm-auto-audit-check -- backend/src
seaorm-auto-audit-check: 1 forbidden write site(s):
  backend/src/users.rs:42: `Entity::insert(` skips the audit hooks — users::Entity::insert(am).exec(db);
```

Comments and string literals are blanked before matching, so documenting the
forbidden styles does not trip the check. `--allow <path>` exempts a directory,
a file, or a bare file name such as `audit.rs`.

### The bulk wrappers

`insert_many`, `update_many`, `delete_many` and `delete_by_id` mirror the SeaORM
methods of the same name, read the affected rows as the before state, run the
write, read the after state back (where the write has one), and write one audit
row per affected row. The redaction rules are the same as the hook path's.

```rust
let txn = db.begin().await?;

seaorm_auto_audit::insert_many::<users::Entity, _, _>(&txn, models).await?;
seaorm_auto_audit::update_many::<users::Entity, _>(&txn, filter, values).await?;
seaorm_auto_audit::delete_many::<users::Entity, _>(&txn, filter).await?;
seaorm_auto_audit::delete_by_id::<users::Entity, _, _>(&txn, id).await?;

txn.commit().await?;
```

The wrappers do not invent their own transaction: run them inside the caller's
transaction, so the writes and their audit rows commit or roll back together.
They also require an audit scope, exactly like the hooks. `update_many`
cannot change a row's primary key: a `values` model that sets a key column is
rejected, because the trail is keyed by the row's existing key.

`insert_many` needs the inserted rows to write their `create` audit rows. On
Postgres and SQLite it reads them back with `RETURNING`. MySQL has no
`RETURNING`, so every model passed to `insert_many` must set its primary key;
with an auto-increment key, insert the rows one at a time inside an audit scope
instead.

## Gotchas

- **`tokio::spawn` does not inherit task-locals.** Code spawned mid-request must
  re-scope with `seaorm_auto_audit::scope(..)`. A spawned write without a scope fails
  loudly rather than writing a half-empty audit row.
- **An audited write outside a scope fails** with
  `DbErr::Custom(seaorm_auto_audit::NO_SCOPE)`. A missing *user* inside a scope is fine:
  the audit row is written with `updated_by_id` NULL.
- **A failed update leaves a stale stash entry.** Harmless: the next write of
  the same row overwrites it, and the stash is keyed by table and primary key so
  rows cannot clobber each other.
- **Interleaved writes to the *same* row in one scope are not supported.** If
  two futures on one task both read a row before either writes it (two branches
  of one request, a `join!`), the second `before_save` overwrites the first
  row's parked state, the first `after_save` consumes it, and the second fails
  with "no before-state". Writes that happen one after another — including a
  graph save — are unaffected, because each write completes both hooks before
  the next begins.
- **Nested `builder().save()` runs the hooks per model.** Children in an object
  graph get audited with the same actor, on the same connection. Keep the graph
  save inside the transaction.

## Tests

```console
$ cargo test -p seaorm-auto-audit --features axum
```

The suite covers the three write paths against SeaORM's `MockDatabase` with the
insert path repeated on Postgres, MySQL and SQLite, plus the bulk wrappers, the
task-local actor and request metadata (including the "no user", "no scope" and
"no request" flows), the redaction rules, and the coverage checker.

The full real-database suite runs against each backend, once for a `uuid`
primary key, once for an integer key and once for a string key, and once for
an unsigned integer key on MySQL only: the SQLite and Postgres drivers cannot
bind a `u64`, so a u64-keyed table cannot be written through them at all.
Postgres and MySQL are skipped when their URL is unset; SQLite always runs:

| backend  | variable              | example                                          |
|----------|-----------------------|--------------------------------------------------|
| Postgres | `DATABASE_URL`        | `postgres://postgres:postgres@localhost:5432/postgres` |
| MySQL    | `MYSQL_DATABASE_URL`  | `mysql://root:password@localhost:3306/test`      |
| SQLite   | `SQLITE_DATABASE_URL` | `sqlite:///tmp/seaorm-auto-audit.db`             |

```console
$ docker run --rm -d --name seaorm-auto-audit-pg -e POSTGRES_PASSWORD=postgres \
    -p 5432:5432 postgres:18-alpine
$ docker run --rm -d --name seaorm-auto-audit-mysql -e MYSQL_ROOT_PASSWORD=password \
    -e MYSQL_DATABASE=test -p 3306:3306 mysql:8
$ DATABASE_URL=postgres://postgres:postgres@localhost:5432/postgres \
  MYSQL_DATABASE_URL=mysql://root:password@localhost:3306/test \
  SQLITE_DATABASE_URL=sqlite:///tmp/seaorm-auto-audit.db \
    cargo test -p seaorm-auto-audit --features axum
```

The SQLite tests default to a temporary file-backed database when
`SQLITE_DATABASE_URL` is unset, so they always run.
